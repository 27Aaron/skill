# Schema and Data Types

Derive structure from business invariants and access patterns first, then pick types.

## Primary keys

| Choice | Use when | Trade-off |
| --- | --- | --- |
| `bigint GENERATED ALWAYS AS IDENTITY` | Single database, compact joins and indexes | Enumerable if exposed; hard to merge across databases |
| `uuid` | IDs generated by many services or offline; merging data; hiding order | Wider keys; random UUIDv4 hurts insert locality — prefer time-ordered UUIDv7 if available |
| Internal key + business key | External ID must be stable while internals change | Two unique constraints to maintain |

An unguessable ID is not authorization.

## Types

- **Strings**: `text`, plus `CHECK (char_length(x) <= n)` for a business limit. `varchar(n)` performs the same; avoid `char(n)` (space padding).
- **Money and exact decimals**: `numeric(p, s)` sized to the real range, or integer minor units plus a currency column.
- **Points in time**: `timestamptz` (stores an instant, not the zone name). Use `date` for calendar dates, and `timestamp` only for local wall-clock values; store the zone separately when needed.
- **`boolean`**: decide whether `NULL` has meaning; if not, add `NOT NULL`.
- **`jsonb`**: for truly dynamic data read as a whole. Fields that are filtered, joined, or constrained belong in columns. Don't use arrays to avoid a join table.

## Constraints

- Encode invariants with `NOT NULL`, `CHECK`, `UNIQUE`, primary keys, and foreign keys. App-side validation is for UX; only constraints hold under concurrency.
- `CHECK` passes on `NULL`, so `CHECK (amount > 0)` doesn't imply `NOT NULL`. Don't fake cross-row constraints with functions; use unique, foreign-key, or exclusion constraints, or locking.
- `UNIQUE` allows many `NULL`s; use `NULLS NOT DISTINCT` (PG 15+) if they should collide. "Unique among non-deleted rows" is a partial unique index: `CREATE UNIQUE INDEX … WHERE deleted_at IS NULL`.
- Case-insensitive uniqueness: a unique index on `lower(email)`, or a `citext` column.
- Specify `ON DELETE` on every foreign key. PostgreSQL doesn't index FK columns automatically; add one when the child is joined on it or the parent is deleted or updated.
- **Multi-tenant integrity**: `project_id REFERENCES projects(id)` alone allows cross-tenant references. Use a composite FK `(tenant_id, project_id) REFERENCES projects (tenant_id, id)`, backed by `UNIQUE (tenant_id, id)` on the parent.
- Defaults apply only when the column is omitted; an explicit `NULL` stays `NULL`. Changing a default doesn't backfill existing rows.

## Review checklist

1. Do keys, uniqueness, and FKs match the real lifecycle?
2. Do types cover the range, precision, time zone, and collation needs?
3. Do the constraints hold under concurrent writes?
4. Do hot filters, joins, and sorts have an index path?
5. Are deletion, archival, and tenant isolation defined?
6. Can the old app version run against the new schema?
